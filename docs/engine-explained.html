The engine, explained

How a battle is simulated, how the solver uses that to pick a move, and why picking one takes seconds. Every number on this page was measured on this repo with scripts/compare_solvers.py and scripts/position_audit.py, on one core of the machine that built it (a Mac, Darwin 25.6); rerun them and yours will differ.

1 · A game is a pure function

Same teams, same seed, same choices: same log. Nothing in the engine reads a clock or global state; all randomness goes through one Rng object (engine/rng.py). That is what lets the solver copy a position, try a pair of choices, throw the copy away and try another.

game.start(teams, seed, format)           -> Battle
game.play_turn(battle, [choice, choice, ...])   changes the Battle, returns it
game.legal_choices(battle, side)          -> every Move and Switch the side could pick
battle.clone(rng=..., record=False)       -> an independent copy for search

2 · Battle → Side → Mon

A Battle holds two Sides, the arena (weather, Trick Room, terrain), the turn number, the winner and the RNG. A Side holds its team (up to six Mons), which team indexes are active, and side conditions (Tailwind, screens). A Mon holds species, moves, stats, HP, status, stat stages, volatile flags, item and ability.

What counts as "the same position"

engine/resolve.state_key lists every field that affects the future. Two outcomes with the same key are merged and their probabilities added. tests/test_resolve.py fails if a field is added to the state without being placed in the key or in the list of fixed fields.

3 · play_turn

  1. validate every choice (a bad one raises before anything changes).
  2. order_actions: sort by kind (switch, Mega, move), then priority, then Speed (Trick Room reverses Speed, not priority). Exact ties are broken with the RNG.
  3. Run the queue. Speed is re-read after every action. A fainted mon loses its action.
  4. End of turn: residual damage and healing, field timers, replacements for fainted mons, winner check.

4 · The move pipeline

pipeline.run_move runs one move through ordered stages. Each stage can stop it.

5 · Hooks

Abilities, items, statuses and move effects are not special-cased in the pipeline. A handler registers itself for a named hook and a cause, and the pipeline fires the hook:

@on("on_hit", "effect:protect")
def protect(battle, ctx): ...

fire(battle, "on_switch_in", mon, [f"ability:{mon.ability}"])

engine/effects_table.py maps every supported move to its effects, and is_supported_move / is_supported_ability / items.is_supported_item tell the live page what the engine cannot play.

6 · Randomness

Random draws are labelled ("damage_roll", "protect", "hit_count"…). Two kinds of RNG sit behind the same interface:

  • Rng: samples, for playing a game.
  • EnumRng: walks a decision tree. Each draw is a branch point; resolve(battle, choices) runs the turn again for every branch and returns [(probability, battle after)]. A damage roll is split into a few buckets, and branches that end in the same state are merged.

The solver uses EnumRng (exact probabilities); rollouts and MCTS use Rng (one sampled future per playout).

7 · How the solver picks

For one turn, list our joint actions (rows) and theirs (columns), resolve every pair under every chance outcome, score each outcome, and average by probability. The result is a matrix game, solved by linear programming (solver/matrix.py) for the mix that guarantees the most. Two turns deep, each outcome is itself solved one level down before averaging. prior.py cuts the actions first, so the table is a few rows and columns, not hundreds.

8 · Why it's slow

Measured on this repo:

9 · Fixes, ranked by payoff

  1. Try the likelier chance outcome first in EnumRng and stop low-probability branches early. In a test this made the live solve 6–9× faster. Not applied.
  2. Cache resolve across the two turns of a search (the same position is reached by several pairs).
  3. Fewer, better options: prior.py already does this; its error is measured by scripts/position_audit.py.
  4. Skip the search: play games instead (see the comparison page).
